## How Rocky wants changes shipped
Rocky isn't a developer. "Do it on the live CRM" is a standing instruction, so every change goes all the way to live without asking:
1. Branch from the latest `origin/main`.
2. Make the change. Bump the cache version in `index.html` (every `?v=NNN` goes up by one, all occurrences).
3. Test it (see below).
4. Commit, push, open a PR into `Rocky-Toky/mr-priceless-crm`, and squash-merge it.
5. Wait for both workflows on the merge commit to go green ("Deploy to GitHub Pages" and, if triggered, "Deploy Supabase functions"), and check the logs when SQL or functions changed.
6. Tell Rocky in plain English what changed and anything he needs to do. No jargon, short.

Never: commit API keys or passwords, print client data or secrets in logs, bulk-edit live client data without asking first, or put model names in commits or PRs.

## Code layout
- `index.html`: every page's markup (sections `#page-<name>`, nav items `data-page` / `data-group`, `data-workspace="sales|delivery|both"`).
- `js/app.js`: the whole app, one big IIFE (~12k lines, vanilla JS, no build step). Key pieces:
  - `DataLayer` loads every table into `state` (`_fetchAllNow` / `_apply` are positional - keep them in step), with realtime in `subscribeRealtime()`.
  - `RENDERERS` maps render functions to pages; `PAGE_GROUPS` holds tabbed menu groups; `FIT_PAGES` holds no-scroll pages.
  - Demo mode (no Supabase config) seeds fake data via `seedDemo()`, which is how pages are tested.
- `js/builtin-playbooks.js`: built-in playbooks (Meeting Structure, Meeting Sit Rate Process). These are only seeded into the DB when the title is missing, so changes to an existing playbook also need a guarded SQL `update`.
- `css/style.css`: tokens on `:root`, gold/black theme.
- `sql/NNN_*.sql`: migrations. They must be safe to re-run. **New ones are added to `.github/workflows/supabase-functions.yml` in two places** (the `paths:` list and the `for f in` loop), and every one in that loop re-runs on each deploy.
- `supabase/functions/*`: Edge Functions. The workflow deploys `sync-client-ads`, `ghl-report-data`, `jarvis`, `send-scheduled-emails`, `sync-client-inbox`, `sync-ghl-leads`, `precall-meetings`, `sync-aircall-calls`, `creative-agent` and `client-portal` (with `--no-verify-jwt`; each checks its own caller). Before anything live changes, the workflow runs `deno test supabase/functions/creative-agent`.

## Access the workflow already has (no keys needed in chat)
GitHub repo secrets: `SUPABASE_ACCESS_TOKEN`, `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_REPLY_TO` (+ optional AI keys, and `AIRCALL_API_ID` / `AIRCALL_API_TOKEN` for recorded calls). `supabase-functions.yml` uses them to:

- lock down auth (sign-ups off)
- set function secrets
- deploy functions

It can also be run by hand (`workflow_dispatch`):
- `test_email`: sends a test email through the scheduled-email sender.
- `create_login`: adds an email to the allowlist, creates a confirmed account, and emails a set-password link.

A Claude session can't reach `*.supabase.co` directly (the sandbox proxy blocks it), so anything touching the live database or auth goes through this workflow.

## Security model
- Only allowlisted, email-confirmed users get data: `public.is_allowlisted()`, and every table has a team-only RLS policy (`sql/066`).
- Lead Follow Up only logins: `allowlist.access = 'leads'` (Carmen, `carmen.noche@gmail.com`, set in sql/100). `is_allowlisted()` only passes `access = 'full'`; sql/100 (`is_lead_caller()`, runs last on every deploy) lets them read/write `client_leads` and `lead_tasks`, read `clients`, `client_ad_creatives`, `client_campaigns`, `lead_sync_status`, `aircall_calls`, `aircall_sync_status`, `employees` and their own allowlist row, and nothing else. Every Edge Function except `sync-ghl-leads` and `sync-aircall-calls` refuses them. In the app, `isLeadsOnly()` (from their allowlist row) locks the workspace to Lead Follow Up, hides the switcher and every other menu item, and sends any other page back to the call queue (`LEADS_ONLY_PAGES`). To test in demo mode, set localStorage `mp_demo_access` to `leads`.
- Server-only tables have RLS on with no policies: `app_secrets`, `client_ghl`, `crm_migrations`.
- Client portal logins (sql/112): in `client_portal_users` (email + client_id), never in the allowlist, so `is_allowlisted()`, `is_lead_caller()` and every Edge Function's allowlist check refuse them. They get no table access at all: everything comes through security-definer `portal_me` / `portal_ads` / `portal_set_notify` (sql/112) and `portal_leads` / `portal_update_lead` / `portal_log_call` / `portal_checkin` / `portal_save_push` / `portal_set_settings` (sql/113), which only return their own client's rows and only client-safe fields (no notes, margin, churn risk - At Risk shows as Live - billing, GHL details, or which team member called: our calls show as "Mr Priceless"). On top, sql/112 adds a restrictive "no client logins" policy (`is_portal_user()`) to every public table with RLS, and storage, and turns RLS on (no change for anyone else) for any public table that has it off; it runs after 100 on every deploy (then 113, which calls `portal_lock_tables()` again for its own tables) so later tables get it too. The only thing open to anyone without signing in is `portal_checkin_link(token)`, which can only hand the one lead its one-off check-in token belongs to over to our team. The team can call the portal functions to preview any client (read-only; `portal_log_call` refuses them). A client login that opens the CRM is sent to `portal/`.
- Sign-in is email + password. Google sign-in has no working Google Cloud project behind it, so don't build on it.
